# 内容生产引擎（Content Engine）参考手册

> 本文档是 content-factory 中「内容生产引擎」的详细展开。
> 源自 `smart-hardware-product-doc`，已升级为通用内容生产框架。

---

## 一、核心哲学

内容不是"写出来的"，而是"搭建出来的"——用通用的结构框架，填入领域特定的内容模块。

**核心目标**：回答四个递进的问题
```
这是什么 → 为什么值得做 → 凭什么能做到 → 对谁有价值
```

**两条铁律**：
1. **原理服务功能**：先说服"方案真实可靠"，再呈现"能力与众不同"
2. **场景放大价值**：一个卖点延伸到越多场景，格局越大

---

## 二、入手逻辑（落笔顺序）

顺应读者"从陌生到信任"的心理，以一条**定位主线**贯穿全文：

```
① 先定产品定位（北极星）
    ↓
② 再给背景（动机）—— 可选，按档案取舍
    ↓
③ 技术/核心原理（建立信任）
    ↓
④ 产品/核心功能（呈现价值）
    ↓
⑤ 方案落地（怎么交付）—— 面向从业者时的核心增量
    ↓
⑥ 应用场景（想象空间）
    ↓
⑦ 可选扩展（市场/竞争/商业）—— 按档案取舍
```

---

## 三、模块化框架详解

### 3.1 核心段（默认必有）

#### ① 产品定位 / 系统架构

**回答**：它是什么？

**内容要点**：
- 一句话定位（北极星）—— 全文地基，所有章节向它收敛
- 核心价值主张
- 系统形态全景（云-边-端 / 分层结构 / 三端架构等）
- 配一张系统架构全景图

**写法提示**：
> 用"X 是 Y 的 Z"句式。例："LED 显控系统是把画面准确映射到大型 LED 屏的大脑与神经。"

---

#### ② 技术原理 / 核心机制

**回答**：凭什么能做？靠不靠谱？

**两种深度（见第四章）**：
- 概览式（浅）：一两句话讲清物理基础
- 深层分支式（深）：逐系统分层拆解

**通用分层模板**（深层分支式用）：

| 分层 | 说明 | 示例（硬件） | 示例（SaaS） |
|------|------|-------------|-------------|
| 感知/采集层 | 数据/信号从哪来 | 传感器、识别模块 | API、埋点、导入 |
| 处理/决策层 | 怎么算、怎么判 | 控制器、算法芯片 | 计算引擎、规则引擎 |
| 执行/输出层 | 结果怎么落地 | 执行机构、显示屏 | 报表、通知、自动化 |
| 通信/传输层 | 数据怎么传 | 总线、无线协议 | HTTP、WebSocket |

**每层要讲四件事**：
1. 物理/工程基础（它靠什么原理工作）
2. 核心实现机制（具体怎么做到的）
3. 演进脉络（从哪一代技术演进而来）
4. 适用边界与局限（什么情况下不好用）

**三条纪律**：
- 分层配图（flowchart / sequenceDiagram）
- 每个分层落到一个可验收的性能指标（不做形容词）
- 原理最终要"闭环回功能"——读完原理，读者自然推出"为什么它可靠/与众不同"

---

#### ③ 核心功能 / 价值

**回答**：具体能干什么？

**内容要点**：
- 核心能力清单（3-5 项核心）
- 增强能力（联动、持续优化、生态集成）
- 落到用户真实收益，而非参数清单
- 每项功能说清"解决了用户的什么问题"

**写法提示**：
> 不要列"功能清单"，要讲"价值清单"。不说"支持人脸打卡"，要说"员工进门即完成打卡，不用再排队刷手机"。

---

#### ④ 方案落地（案例 + 流程图）

**回答**：怎么交付？实际怎么用？

> 面向从业者/集成商时，这是全文最有价值的增量。**两个要素缺一不可。**

**要素一：现实案例**

每个案例遵循一条链：
```
场景痛点 → 方案设计 → 流程/拓扑图 → 技术选型要点 → 安装要点 → 配置与调试 → 交付验收 → 对用户的价值
```

案例要当"真实的场景"来写，给出可落地的选型依据，贴近生活、避免空泛。

**要素二：设计流程图**

用 Mermaid 画主流程与点位/数据流：
- 通用主流程：`需求梳理 → 规划 → 选型 → 实施 → 配置 → 验收`（flowchart TD）
- 每个案例补充点位拓扑或状态流转（flowchart LR / sequenceDiagram）
- 所有图配图注

---

#### ⑤ 应用场景

**回答**：给谁用？用在哪？

每个场景遵循"痛点→方案→价值"三段式：
- **痛点**：这个场景下用户遇到什么问题？
- **方案**：本产品怎么解决这个问题？
- **价值**：用了之后带来什么具体收益？

场景数量：3-5 个为宜，覆盖主要应用领域。

---

### 3.2 可选扩展段（按档案取舍）

#### 市场背景与痛点

**何时写**：面向决策层/采购、对外宣传时

**内容要点**：
- 行业规模与增速（必须有来源）
- 政策与升级驱动
- 既有方案的痛点
- 由此引出的需求

**纪律**：市场数据必须有来源并标注；无来源就不写具体数字。

---

#### 竞争格局 / 多玩家对比

**何时写**：面向决策层/采购、行业综述时

**内容要点**：
- 竞争格局图谱（主流玩家分类）
- 对比矩阵（核心维度横向对比）
- 核心壁垒与差异化
- 成本与交付优势

---

#### 商业模式与趋势

**何时写**：面向决策层/投资者、行业综述时

**内容要点**：
- 交付形态（产品 / 解决方案 / 服务 / SaaS）
- 盈利模式（一次性 / 订阅 / 按用量 / 分成）
- 未来路线图与技术趋势
- 市场空间与增长逻辑

---

## 四、三种标准档案（预设配置）

### 深度技术档案

**受众**：从业者 / 集成商 / 工程端

**结构**：① ②(深层分支式) ③ ④(案例+流程) ⑤

**特点**：跳过市场与多厂商对比，篇幅让给原理与落地

---

### 决策采购档案

**受众**：决策层 / 采购 / 管理层

**结构**：① 市场 ③功能 竞争对照 商业模式

**特点**：原理点到为止，强化市场与格局

---

### 聚焦系统本体档案

**受众**：明确要求"只讲系统本身"时

**结构**：只写 ① ② ③ ④ ⑤

**特点**：强制删除市场数据与厂商横向对比，不因惯性保留

**执行原则**：若用户明说"删除产品市场情况、多厂商对比、只聚焦产品系统本身"，直接切到此档案。

---

## 五、受众-内容偏向矩阵

| 受众 | 核心诉求 | 内容侧重 | 证据/配图 | 语气 |
|------|---------|---------|----------|------|
| 决策/管理层 | 值不值、前景、ROI | 市场、价值、壁垒、商业模式 | 行业规模与趋势、格局对比 | 凝练、有格局 |
| 采购/选型者 | 能不能用、性价比 | 功能、参数、方案对比 | 参数表、对比矩阵、标杆案例 | 中立、理性 |
| 工程/实施人员 | 怎么搭、怎么选、怎么维护 | 系统架构、参数选型、落地案例 | 架构图、参数表、实施要点 | 专业、直接 |
| 普通读者/科普 | 是什么、有什么用 | 定位、通俗原理、生活场景 | 类比、示意、场景图 | 通俗、易懂 |

**关键实践**：
- 面向工程端时，插入"核心参数与选型"章 + "实际案例与设计方案"四段式
- 面向决策层则反之：弱化参数，强化市场与格局
- 落到文章开头：把受众写进引言或封面副题，例如"**面向工程端**"

## 六、写作规范

### 6.1 通用质量标准

- 内容丰富、结构清晰；明确立场与判断，作者视角清楚
- 关注读者真正关心的价值，而非堆参数
- 读者可能质疑处给出理由
- 每个术语第一次出现给出通俗解释

### 6.2 反对的写法

- ❌ "清单口号式"标题或正文（"X 大优势""终极指南"）
- ❌ 空话套话与空洞形容词
- ❌ "进行/开展/实施 + 名词"的虚词结构（直接用动词）
- ❌ 无依据的"确保/显著+无量化"（换成可量化标准）
- ❌ 结论在多章重复三遍（一处给结论，其余章补新证据或新角度）
- ❌ 非必要的"参考资料/致谢"等小节
- ❌ 标题用表格化模板口号；每章首句重复标题

### 6.3 证据与数据纪律

- 参数类给**区间 / 工程基准**，能核实尽量给来源
- 无法核实的必须标注"示例 / 演示估算 / 行业通用基准"
- **禁止编造市场数字**
- 市场类规模、增速数据必须有来源并标注；无来源就不写具体数字

### 6.4 排版纪律

- 加粗仅用于专有名词、工具名、关键概念；每段加粗 ≤ 3 处
- 禁止加粗+斜体叠加
- 默认不使用 emoji（除非明确要求）
- 中文标点规范，避免中英标点混用

## 七、配图与封面规范

### 7.1 图片分类与选型

| 图片类型 | 用途 | 制作方式 | 要求 |
|---------|------|---------|------|
| 架构图 | 展示系统结构 | 矢量框线示意图（Mermaid/Python/CSS） | 标注清晰、线型语义一致 |
| 流程图 | 展示流程/状态流转 | Mermaid flowchart/sequenceDiagram | 正交分支、无悬空箭头 |
| 对比图 | 展示数据对比 | 表格 / 柱状图 | 数据有来源 |
| 场景图 | 展示应用场景 | AI 生成 / 实拍 | 标注"示意图" |
| 封面图 | 文章封面 | AI 底图 + 文字叠加 | 无水印、高对比度 |

### 7.2 关键纪律

- **架构图/流程图不用 AI 位图承载结构信息**——AI 生成图里的标注文字易错乱，不可靠
- **场景图/封面可用 AI 生成**，构图层要求"无文字、无水印"，对外发布标注"示意图/概念图"
- 若成品图带"AI生成"水印，用背景色填充 + 边缘羽化去除，而非直接裁剪
- **统一存储**：多端共用的图像统一为 PNG，用相对路径引用
- **封面文字叠加**：大字号 + 深色半透明圆角底衬 + 白字（保证对比度）；在干净底图上一步完成，避免多次叠加产生叠影
- 所有插图需配图注；**凡承载证据的图必须有图注与来源**

## 八、从大纲到成品的标准工作流

```
① 锁定受众 → ② 选档案 → ③ 定结构 → ④ 定深度 → ⑤ 补证据 → ⑥ 规划图 → ⑦ 产出制品
```

| 步骤 | 操作 | 关键决策 |
|------|------|---------|
| ① 锁定受众 | 用受众矩阵确定目标读者 | 决定参数密度、篇幅与结构 |
| ② 选档案 | 深度技术 / 决策采购 / 聚焦本体 | 决定核心段和扩展段的取舍 |
| ③ 定结构 | 结构化 / 叙事化 / 混合式 | 技术分析用结构化，产品发布用叙事化 |
| ④ 定深度 | 概览式 / 深层分支式 | 工程端用深层，决策层用概览 |
| ⑤ 补证据 | 标注数据来源口径 | 无来源标注"演示估算"，禁止编造 |
| ⑥ 规划图 | 确定需要哪些图 | 架构/流程用矢量，场景/封面用 AI |
| ⑦ 产出制品 | 调用成品技能输出 | HTML→html-report、Word→docx、MD→直接写 |

## 九、复用示例

### 示例一：门禁设备（深度技术档案）

- **定位**：以身份凭证为入口、串联识别—决策—执行—留痕的出入口控制基础设施
- **原理（深层分支）**：感知层（RFID/指纹/人脸/静脉物理原理 + 活体 + FAR/FRR）→ 决策层（人—门—时段权限矩阵 + 离线策略）→ 执行层（磁力锁/电插锁/电控锁原理）→ 通信层（韦根 vs OSDP + 云边端时序）
- **落地**：写字楼无感通行、老旧社区+电动车管控、数据中心双人授权三案例 + 通用设计流程图

### 示例二：振动光纤（决策采购档案）

- **定位**：一根光纤即一条无形警戒线的智能周界感知终端
- **原理（概览）**：瑞利散射 + 相位敏感光时域反射（Φ-OTDR/DAS）沿线分布式定位
- **差异化卖点**：单端覆盖数十公里、全程无源、抗电磁干扰、耐腐蚀免维护

### 示例三：迁移到 SaaS 领域（CRM 产品）

- **定位**：把客户全生命周期数据化、流程化、自动化的营收增长引擎
- **原理（深层）**：数据采集层（表单/埋点/导入）→ 处理层（客户画像/评分/分级）→ 执行层（自动化工作流/报表）→ 集成层（API/OpenAPI）
- **落地**：B2B 企业销售流程、SaaS 客户成功管理、电商会员运营三案例

> 换一款产品/一个领域时，先选定档案，再把对应段的原理、落地与扩展段按规范替换即可。框架本身零改动。
