# Content Factory — 端到端内容生产与发布工厂

> **核心理念**：把内容生产变成一条可配置、可迁移、可规模化的流水线。框架通用，领域知识通过配置注入，换赛道只需换配置包。

---

## 一、适用场景

| 场景 | 对应模块 | 说明 |
|------|---------|------|
| 批量生产某领域系列文章 | 内容生产引擎 | 按统一框架批量产出高质量内容 |
| 管理内容排期与选题池 | 产品池管理 | 待办池 + 已发布记录 + 进度追踪 |
| 自动发布到静态博客 | 发布部署引擎 | 纯前端博客 + Gitee/GitHub Pages 部署 |
| 每日/每周定时产出 | 全流水线 | 定时触发 → 取题 → 生产 → 发布 → 验证 |
| 切换到新内容领域 | 全框架迁移 | 替换领域配置包，框架零改动 |

```
│ 分类体系     │ 技术原理双深度     │ Gitee → GitHub Pages  │
│ 进度追踪     │ 方案落地+流程图    │ CDN 缓存绕过          │

                    ┌─────────┴─────────┐

```

**可迁移性设计原则**：
1. **框架与内容解耦**：写作框架、发布流程、管理工具完全通用
2. **配置驱动**：所有领域特定信息都在 JSON/MD 配置文件中
3. **输出格式无关**：内容引擎产出结构化内容，可渲染为 HTML/MD/PDF/Docx
4. **渐进式采用**：三大引擎可独立使用，也可串联成完整流水线

## 三、引擎一：产品池管理（Pool Manager）

### 3.1 核心数据结构

**产品池文件**（如 `product_pool.json`）：
```json
{
  "description": "内容选题池描述",
  "categories": {
    "category-id": "分类中文名"
  },
  "products": [
    {
      "slug": "url-friendly-id",
      "name": "内容标题",
      "category": "category-id",
      "audience": "目标受众（工程端/决策层/科普等）",
      "one_liner": "一句话定位，作为写作北极星"
    }
  ]
}
```

**已发布记录**（如 `published.json`）：
```json
{
  "published": [
    {
      "slug": "article-slug",
      "name": "文章标题",
      "category": "category-id",
      "date": "2026-01-01",
      "auto_generated": true
    }
  ]
}
```

### 3.2 标准操作

| 操作 | 说明 | 典型用法 |
|------|------|---------|
| `next` | 取下一个待发布内容 | 每日任务自动取题 |
| `list` | 列出已发布内容 | 查看进度 |
| `status` | 查看总进度 | 周报/月报 |
| `mark` | 标记为已发布 | 发布成功后调用 |
| `add` | 新增选题到池中 | 扩充选题库 |

### 3.3 迁移到新领域

只需替换 `product_pool.json` 中的 `categories` 和 `products` 数组。管理逻辑零改动。

## 四、引擎二：内容生产引擎（Content Engine）

> 源自 `smart-hardware-product-doc`，已升级为通用内容生产框架。

### 4.1 核心写作框架（模块化，非固定模板）

**核心段（默认必有，聚焦内容本体）**：

| 段 | 回答的问题 | 内容要点 |
|---|----------|---------|
| ① 定位 / 系统架构 | 它是什么 | 一句话定位、价值主张、系统形态全景 |
| ② 核心原理 | 凭什么能做 | 物理/机制基础与实现路径，深度可选 |
| ③ 核心功能 / 价值 | 能干什么 | 能力清单，落到用户真实收益 |
| ④ 方案落地（案例+流程） | 怎么交付 | 现实案例 + 流程图 + 选型要点 |
| ⑤ 应用场景 | 给谁用 | 分场景"痛点→方案→价值" |

**可选扩展段（按受众档案取舍）**：

| 段 | 何时加入 |
|---|---------|
| 市场背景与痛点 | 面向决策层/采购、对外宣传 |
| 竞争格局 / 多玩家对比 | 面向决策层/采购、行业综述 |
| 商业模式与趋势 | 面向决策层/投资者 |

### 4.2 受众-内容偏向矩阵（先定受众，再定一切）

| 受众 | 核心诉求 | 内容侧重 | 语气 |
|------|---------|---------|------|
| 决策 / 管理层 | 值不值、前景、ROI | 市场、价值、壁垒、商业模式 | 凝练、有格局 |
| 采购 / 选型者 | 能不能用、性价比 | 功能、参数、方案对比 | 中立、理性 |
| 工程 / 实施人员 | 怎么搭、怎么选、怎么维护 | 系统架构、参数选型、落地案例 | 专业、直接 |
| 普通读者 / 科普 | 是什么、有什么用 | 定位、通俗原理、生活场景 | 通俗、易懂 |

### 4.3 三种标准档案（预设配置）

- **深度技术档案**（面向从业者）：① ②深层 ③ ④(案例+流程) ⑤。跳过市场与对比。
- **决策采购档案**（面向管理层）：① 市场 ③功能 竞争对照 商业模式。原理点到为止。
- **聚焦系统本体档案**：只写①②③④⑤，强制删除市场数据与横向对比。

### 4.4 原理双深度

- **概览式**：一两句话讲清物理基础，只为功能背书。适合宣传、决策。
- **深层分支式**：逐系统分层拆解，每层讲四件事：物理基础、核心机制、演进脉络、适用边界。分层配图 + 落到可验收指标。

### 4.5 配图与封面规范

- **架构/流程图**：用矢量框线示意图（Mermaid / Python / CSS），**不用 AI 位图承载结构信息**
- **场景图/封面**：可用 AI 生成，要求"无文字、无水印"，对外标注"示意图"
- **封面文字**：大字号 + 深色半透明圆角底衬 + 白字，保证对比度
- **所有承载证据的图必须配图注与来源**

### 4.6 迁移到新领域

写作框架完全通用。迁移时只需：
1. 替换领域专有名词库（如果需要）
2. 调整"原理"部分的分层模板
3. 更新案例库的行业场景

框架本身零改动。

## 五、引擎三：发布部署引擎（Publish Engine）

> 源自 `blog-publish`，纯前端静态博客方案。

### 5.1 博客系统架构

```
blog/
├── index.html              # 首页（Hero + 文章列表 + 分类筛选）
├── article.html            # 文章阅读页（封面 + 目录 + 正文）
├── articles.json           # 文章清单（核心配置文件）
├── CNAME                   # 自定义域名（可选）
├── articles/               # 文章文件夹（每篇一个子目录）
│   └── {slug}/
│       ├── {file}.md       # Markdown 文章
│       └── images/         # 文章图片
└── assets/
    ├── css/style.css       # 主题样式（深色/浅色双主题）
    └── js/
        ├── main.js         # 首页逻辑
        └── article.js      # 文章页逻辑（MD 解析 + TOC）
```

**技术特点**：
- 纯前端，零后端依赖，迁移零成本（整个文件夹拷贝即可）
- Markdown 客户端渲染，新增文章无需构建
- 支持明暗主题、分类筛选、阅读目录、上/下篇

### 5.2 articles.json 核心配置

```json
{
  "site": {
    "title": "站点名称",
    "subtitle": "副标题",
    "description": "站点简介"
  },
  "categories": [
    { "id": "cat-id", "name": "分类中文名" }
  ],
  "articles": [
    {
      "slug": "article-slug",
      "title": "文章标题",
      "category": "cat-id",
      "date": "2026-01-01",
      "cover": "images/cover.png",
      "file": "文章.md",
      "readTime": 20,
      "excerpt": "一句话摘要"
    }
  ]
}
```

> ⚠️ **JSON 语法纪律**：字符串中**绝对不要使用中文双引号 `""`**，改用「」或 ''，否则解析失败全站白屏。

### 5.3 Gitee 镜像 → GitHub Pages 部署方案

**为什么用镜像方案**：国内直连 Gitee 秒推，无需代理/VPN。

```
git push gitee main
    ↓ 秒推（国内直连）
Gitee 仓库更新
    ↓ Gitee 镜像同步（自动，几秒~几分钟）
GitHub 仓库更新
    ↓ GitHub Pages 自动重建（1~2 分钟）
GitHub Pages 更新
    ↓ CDN 缓存
线上站点更新
```

**配置要点**：
- 本地添加两个 remote：`origin`(GitHub) 和 `gitee`(Gitee)
- Gitee 仓库配置"镜像推送"到 GitHub
- 使用 GitHub Classic Token（repo 权限）作为镜像认证

### 5.4 发布五步验证法

按顺序验证，不要跳步：

1. **确认 Gitee 已更新**：`git fetch gitee ; git log gitee/main -3`
2. **确认 GitHub 已同步**：WebFetch 访问 `https://api.github.com/repos/{user}/{repo}/commits?per_page=3`
3. **确认 articles.json 已更新**：访问 `https://{domain}/articles.json?v={时间戳}`（时间戳绕过 CDN）
4. **确认首页动态渲染正确**：用浏览器验证（WebFetch 不执行 JS）
5. **如未更新**：等待 CDN 缓存过期或 Ctrl+Shift+R 强制刷新

### 5.5 CDN 缓存绕过方案

GitHub Pages 默认 10 分钟 CDN 缓存。绕过方法：
- JS 中 fetch 请求加时间戳：`articles.json?v=${Date.now()}`
- 更新 HTML 中 JS 引用的版本号 `?v=N`

### 5.6 迁移到新博客

只需：
1. 替换 `articles.json` 中的 `site` 信息
2. 替换 `articles/` 下的文章内容
3. 修改 Git remote 地址
4. 更新 CNAME（如换域名）

框架零改动。

## 六、完整流水线工作流（每日自动产出）

### 6.1 标准七步流程

```
① 取题 → ② 生产内容 → ③ 准备目录 → ④ 注册文章 → ⑤ 推送部署 → ⑥ 验证 → ⑦ 标记完成
```

详细步骤：

| 步骤 | 操作 | 输入 | 输出 |
|------|------|------|------|
| ① 取题 | 从产品池取下一个待发布 | product_pool.json + published.json | 产品信息（slug/name/category/audience/one_liner） |
| ② 生产内容 | 按内容引擎规范生成文档 + 配图 | 产品信息 + 受众档案 | MD 文档 + 封面图 + 架构/流程图 |
| ③ 准备目录 | 整理到博客文章目录结构 | 生成的内容 | `blog/articles/{slug}/` 完整目录 |
| ④ 注册文章 | 在 articles.json 中追加条目 | 文章元信息 | 更新后的 articles.json |
| ⑤ 推送部署 | git add/commit/push 到 Gitee | 本地更改 | 远程仓库更新 |
| ⑥ 验证 | 五步验证法 | — | 发布成功确认 |
| ⑦ 标记完成 | 在 published.json 中记录 | 产品信息 | 更新后的发布记录 |

### 6.2 质量门禁（发布前必查）

- [ ] 文档标题与封面图标题一致
- [ ] 封面图已嵌入并标注"示意图"
- [ ] 架构图/流程图无悬空箭头、线型语义一致
- [ ] 参数数据有来源标注或"工程基准/演示估算"
- [ ] articles.json 语法正确（无中文双引号、逗号正确）
- [ ] 本地预览渲染正常
- [ ] slug 在产品池中存在且未重复

## 七、迁移到新领域指南

### 7.1 迁移清单

| 模块 | 需要替换的内容 | 不需要改动的部分 |
|------|--------------|----------------|
| 产品池 | categories + products 列表 | 管理逻辑、CRUD 操作、状态追踪 |
| 内容引擎 | 领域术语、原理分层模板、案例库 | 写作框架、受众矩阵、模块化结构、配图规范 |
| 发布引擎 | site 信息、文章内容、域名/仓库地址 | 博客系统架构、JS 逻辑、样式、部署流程 |
| 流水线 | 领域配置包 | 七步流程、质量门禁、验证方法 |

### 7.2 迁移步骤（换赛道只需 5 步）

1. **准备领域配置包**：新建 `{领域}-pool.json`，填好分类和选题列表
2. **初始化博客**：拷贝 blog 模板 → 修改 site 信息 → 清空 articles → 配置 Git 仓库
3. **调整写作预设**（可选）：根据领域特点调整原理分层模板
4. **跑通第一篇**：手动走一遍完整流水线，验证全链路
5. **开启自动化**：配置定时任务，进入自动产出模式

### 7.3 可迁移的领域示例

本框架已在智能硬件领域验证，同样适用于：

- **SaaS / 软件产品**：把"技术原理"换成"产品架构"，"落地案例"换成"客户案例"
- **消费品 / 品牌**：把"工程选型"换成"用户画像"，"技术原理"换成"设计理念"
- **行业研究 / 报告**：把"产品"换成"赛道"，"功能"换成"格局分析"
- **教程 / 课程**：把"产品定位"换成"学习目标"，"案例"换成"练习题"

## 九、与原 Skill 的关系

本 Skill 是 `smart-hardware-product-doc` + `blog-publish` + `auto_publish` 三者的**统一升级**：

| 原 Skill / 模块 | 在 Content Factory 中的位置 | 升级点 |
|----------------|---------------------------|--------|
| smart-hardware-product-doc | 内容生产引擎 | 从"硬件专用"升级为"通用框架"，领域知识配置化 |
| blog-publish | 发布部署引擎 | 保留完整发布流程，明确迁移路径 |

```
使用 content-factory，从产品池中取下一个待发布内容，
面向<受众>生成完整的内容套件（MD + 封面 + 架构图），
```

**只管理选题池：**

```
使用 content-factory 的产品池管理功能，

```
